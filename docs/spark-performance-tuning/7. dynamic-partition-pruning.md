## Dynamic Partition Pruning (DPP)

Dynamic Partition Pruning (DPP) is Spark’s mechanism for pushing filter conditions from a join’s inner table to the outer table’s partition scan — even when those filter conditions aren’t known until query planning time.<br>

Consider this query:

```sql
SELECT o.*, c.coutry 
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE c.country = 'Germany'
```

Without DPP, Spark scans all partitions of orders then joins, then filters. <br>
With DPP, Spark first determines which customer_ids belong to Germany, then uses that set to prune the orders table scan — only reading order partitions that contain German customers.

```python
spark.conf.set("spark.sql.optimizer.dynamicPartitionPruning.enabled", "true")
```

**Requirements for DPP to Trigger**<br>
DPP only activates under specific conditions:<br>
- The large table must be partitioned on the join key
- The filter must be on the small (dimension) table
- The small table side must be broadcastable (or DPP creates a subquery that’s executed first)<br>

This is why the star schema pattern (fact table + dimension tables) maps so naturally to DPP — your large fact table is partitioned on foreign keys, and your small dimension tables carry the filter conditions.<br>

**Verifying DPP in the Query Plan**<br>
When DPP is active, you’ll see a `DynamicPruningExpression` in your Physical Plan output. This is your confirmation that Spark is skipping irrelevant partitions.
